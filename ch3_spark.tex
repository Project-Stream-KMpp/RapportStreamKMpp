\chapter{Apache Spark}
\label{ch:spark}

La thèse de référence présente le modèle d'exécution d'Apache Flink avant de détailler l'implémentation distribuée de StreamKM++. Une démarche similaire est adoptée ici avec Apache Spark. Ce chapitre se concentre uniquement sur les mécanismes utilisés dans le projet : les RDD et les DataFrames, le traitement par micro-batches avec Structured Streaming, les variables diffusées, la réduction arborescente et le partitionnement des données.

L'objectif n'est donc pas de proposer une présentation générale de Spark, mais d'identifier les mécanismes qui interviennent directement dans l'adaptation de StreamKM++. Leur mise en œuvre dans le projet est présentée au chapitre~\ref{ch:implementation}.

% ---------------------------------------------------------------------------
\section{RDD et DataFrames}
% ---------------------------------------------------------------------------

Apache Spark fournit plusieurs abstractions pour le traitement distribué des données. Deux d'entre elles sont utilisées dans l'implémentation : les \emph{Resilient Distributed Datasets} (RDD) et les DataFrames.

Un RDD est une collection de données distribuée et partitionnée. Les transformations telles que \texttt{map}, \texttt{filter} ou \texttt{mapPartitions} peuvent être appliquées indépendamment aux différentes partitions. Cette abstraction est adaptée aux objets \texttt{Point} manipulés par StreamKM++, dont le traitement repose notamment sur le calcul de distances, la construction de coresets et la mise à jour des structures de \emph{merge-and-reduce}.

Les DataFrames représentent quant à eux des données distribuées organisées selon un schéma. Ils permettent à Spark d'appliquer ses mécanismes d'optimisation aux opérations structurées telles que les projections, les filtres et les agrégations.

Dans l'architecture retenue, les DataFrames sont principalement utilisés pour l'entrée des données et l'intégration avec Structured Streaming. La logique algorithmique de StreamKM++ est ensuite exécutée à partir de RDD contenant des objets \texttt{Point}. Cette séparation permet de conserver une logique algorithmique distincte des mécanismes d'orchestration propres à Spark.

\section{Traitement par micro-batches avec Structured Streaming}
% ---------------------------------------------------------------------------

Structured Streaming permet de traiter des flux de données en s'appuyant sur les mécanismes d'exécution de Spark. Dans le cadre de ce projet, le traitement repose sur le mode \emph{micro-batch}.

Le flux d'entrée est découpé en lots successifs, chacun étant traité comme un ensemble de données borné. La méthode \texttt{foreachBatch} permet d'appliquer un traitement spécifique à chaque micro-batch produit par le moteur.

Ce fonctionnement est différent du modèle de streaming utilisé dans l'implémentation Flink étudiée par Bitsakis. Avec Structured Streaming, chaque micro-batch constitue directement une unité de traitement identifiable. Le lot peut ainsi être traité de manière distribuée avant que le résumé obtenu soit intégré à l'état maintenu par l'application.

Cette approche implique toutefois que les observations sont traitées par lots et non individuellement dès leur arrivée. Le traitement dépend donc de la fréquence de déclenchement des micro-batches. Les conséquences de ce choix sont discutées au chapitre~\ref{ch:discussion}.

\section{Diffusion des centres avec \texttt{broadcast}}
% ---------------------------------------------------------------------------

Certaines opérations nécessitent qu'une même information soit accessible aux différentes tâches Spark. C'est notamment le cas lors de l'évaluation du clustering, où les centres calculés doivent être utilisés par toutes les partitions contenant les observations.

Spark fournit pour cela des variables diffusées, ou \emph{broadcast variables}. Une valeur diffusée est transmise aux exécuteurs afin d'être réutilisée localement par les tâches qui en ont besoin. Ce mécanisme évite de transférer plusieurs fois la même donnée avec chaque tâche.

Dans l'implémentation, ce mécanisme est utilisé par \texttt{CostEvaluator.cost}. Les centres du clustering sont diffusés aux exécuteurs, puis chaque partition calcule localement sa contribution à la somme des erreurs quadratiques. Les contributions partielles sont ensuite agrégées afin d'obtenir le coût global.

La mise en œuvre de cette évaluation est détaillée dans la section~\ref{sec:impl-evaluation}.

\section{Réduction arborescente}
\label{sec:spark-treereduce}
% ---------------------------------------------------------------------------

La construction distribuée de StreamKM++ produit plusieurs résumés intermédiaires, généralement un par partition. Ces résumés doivent ensuite être combinés afin de construire un coreset global.

Une approche simple consisterait à récupérer l'ensemble des résumés sur le driver puis à effectuer les fusions séquentiellement. Cette organisation centraliserait toutefois l'ensemble du travail de réduction sur un seul processus.

Spark fournit des opérations de réduction arborescente telles que \texttt{treeReduce} et \texttt{treeAggregate}. Les résultats intermédiaires sont alors combinés progressivement à plusieurs niveaux avant l'obtention du résultat final. La fusion peut ainsi être partiellement distribuée au lieu d'être réalisée entièrement sur le driver.

Ce principe est adapté à StreamKM++, puisque deux résumés peuvent être fusionnés puis réduits afin de produire un nouveau coreset pouvant lui-même être combiné avec un autre résumé.

Dans l'implémentation réalisée, \texttt{treeReduce} est utilisé pour fusionner les structures \texttt{BucketManager} construites sur les différentes partitions. Cette organisation permet de conserver une construction locale indépendante pour chaque partition avant la production du résumé global.

La réduction arborescente permet ainsi d'éviter une centralisation immédiate de toutes les opérations de fusion. Son influence sur les performances est étudiée expérimentalement dans le chapitre consacré à l'évaluation.

\section{Partitions et ressources de calcul}
\label{sec:spark-partitions-coeurs}
% ---------------------------------------------------------------------------

Le partitionnement constitue un élément central du modèle d'exécution de Spark. Un RDD est divisé en plusieurs partitions, chacune pouvant être traitée par une tâche indépendante.

Dans l'implémentation de StreamKM++, chaque partition construit son propre \texttt{BucketManager} et produit un résumé local des observations qu'elle contient. Le nombre de partitions détermine donc le nombre de constructions locales et influence la manière dont les différents coresets sont ensuite fusionnés.

Le nombre de partitions doit être distingué des ressources de calcul disponibles. Le premier détermine la décomposition logique des données et le nombre de tâches susceptibles d'être exécutées, tandis que le nombre de c\oe{}urs disponibles détermine le nombre de tâches pouvant effectivement être exécutées simultanément.

Une augmentation du nombre de partitions n'entraîne donc pas nécessairement une amélioration des performances. Un partitionnement plus fin peut accroître les possibilités de parallélisme, mais également augmenter le nombre de tâches ainsi que les coûts liés à leur ordonnancement, à la sérialisation des données et aux opérations de fusion.

Le partitionnement peut également influencer le coreset produit. Chaque partition réalise en effet une construction locale indépendante avant la fusion des résultats. Modifier le découpage des données peut ainsi conduire à des résumés intermédiaires différents et, par conséquent, à un coreset global légèrement différent.

Cette distinction est importante pour comprendre le comportement de l'implémentation distribuée et l'influence du partitionnement sur la construction des coresets.
