\chapter{Évaluation expérimentale}
\label{ch:evaluation}

Ce chapitre présente l'implémentation de StreamKM++ avec Apache Spark.
L'objectif est de montrer comment les mécanismes décrits au
chapitre~\ref{ch:spark} sont utilisés pour distribuer les différentes étapes
de l'algorithme présenté au chapitre~\ref{ch:algorithmes}.

L'implémentation repose sur une séparation entre les composants algorithmiques
et l'orchestration distribuée. Les calculs liés à k-means, au coreset tree et
au merge-and-reduce restent dans les packages \texttt{streamkm.core} et
\texttt{streamkm.coreset}. La couche \texttt{streamkm.spark} organise leur
exécution sur les partitions Spark, la fusion des résultats intermédiaires et
le traitement des micro-batches.

Le portage est présenté en quatre étapes : la construction distribuée d'un
coreset sur un jeu de données borné, le calcul distribué de la qualité du
clustering, l'adaptation à Structured Streaming, puis une synthèse des
principales différences entre l'implémentation Flink de référence et la
version Spark développée dans ce projet.


% ---------------------------------------------------------------------------
\section{Construction distribuée du coreset}
\label{sec:impl-dataflow}
% ---------------------------------------------------------------------------

La construction distribuée suit le principe général de StreamKM++ : chaque
sous-ensemble des données est d'abord résumé localement, puis les résumés
obtenus sont fusionnés pour produire un coreset global.

Dans Spark, les partitions du RDD fournissent naturellement ces sous-ensembles.
Chaque partition peut donc exécuter indépendamment le même traitement
merge-and-reduce avant la phase de fusion.


% ---------------------------------------------------------------------------
\subsection{Coresets locaux par partition}
% ---------------------------------------------------------------------------

La méthode \texttt{StreamKMPlusPlus.partialCoresets} construit un coreset
indépendant pour chaque partition du RDD.

\begin{verbatim}
def partialCoresets(
  rdd: RDD[Point],
  p: StreamKMParams
): RDD[Array[Point]] = {

  rdd.mapPartitionsWithIndex { (idx, it) =>
    val bm = new BucketManager(
      p.m,
      p.seed + idx
    )

    bm.insertAll(it)

    Iterator.single(
      bm.extractCoreset()
    )
  }
}
\end{verbatim}

Chaque partition crée son propre \texttt{BucketManager} puis consomme
séquentiellement les points qui lui sont attribués. La construction du
coreset local utilise donc exactement la même logique que la version
séquentielle de StreamKM++, mais appliquée indépendamment sur chaque
partition.

Une graine dérivée de l'indice de partition est utilisée :

\begin{verbatim}
p.seed + idx
\end{verbatim}

Ce choix permet de conserver un comportement reproductible lorsque le nombre
de partitions reste identique, tout en évitant que plusieurs partitions
utilisent exactement la même suite pseudo-aléatoire.

Le résultat de cette étape est un RDD contenant un résumé pondéré par
partition. Ces résumés doivent ensuite être combinés pour obtenir une
représentation globale des données.


% ---------------------------------------------------------------------------
\subsection{Fusion arborescente des coresets}
% ---------------------------------------------------------------------------

Dans l'implémentation Flink étudiée par Bitsakis, les coresets partiels sont
réunis par un opérateur final exécuté avec un parallélisme limité. Dans notre
version Spark, cette étape est exprimée à l'aide de \texttt{treeReduce}.

\begin{verbatim}
def mergeCoresets(
  rdd: RDD[Point],
  p: StreamKMParams,
  depth: Int = 2
): Array[Point] = {

  val perPartition =
    rdd.mapPartitionsWithIndex { (idx, it) =>

      val bm =
        new BucketManager(
          p.m,
          p.seed + idx
        )

      bm.insertAll(it)

      Iterator.single(bm)
    }

  perPartition
    .treeReduce(
      (a, b) => a.merge(b),
      depth
    )
    .extractCoreset()
}
\end{verbatim}

Chaque élément de \texttt{perPartition} est donc un
\texttt{BucketManager} construit localement. L'opération :

\begin{verbatim}
a.merge(b)
\end{verbatim}

réutilise directement la logique de fusion définie dans la couche
\texttt{streamkm.coreset}. Deux résumés peuvent ainsi être combinés puis
réduits avant d'être fusionnés à un niveau supérieur.

L'utilisation de \texttt{treeReduce} évite de transférer immédiatement tous
les résultats intermédiaires vers le driver pour les fusionner un à un. Les
combinaisons sont organisées sur plusieurs niveaux, ce qui permet à une partie
du travail de réduction d'être réalisée de manière distribuée.

Cette organisation constitue une différence importante avec le dataflow Flink
de référence. Son effet réel sur les performances n'est toutefois pas supposé
a priori et sera évalué dans les expériences de scalabilité du
chapitre~\ref{ch:evaluation}.


% ---------------------------------------------------------------------------
\subsection{Calcul du clustering final}
% ---------------------------------------------------------------------------

Une fois le coreset global obtenu, le clustering final est calculé avec
\texttt{KMeans.fit}.

Cette étape reprend directement les composants présentés au
chapitre~\ref{ch:algorithmes} : initialisation k-means++, exécution de
l'algorithme de Lloyd pondéré et conservation du meilleur résultat parmi les
redémarrages réalisés.

Le coreset final étant de taille limitée par le paramètre $m$, cette étape
s'exécute sur le driver. Le parallélisme intervient donc principalement dans
la construction et la fusion des résumés, et non dans l'exécution finale de
k-means++ sur le coreset.

\section{Évaluation distribuée du coût}
\label{sec:impl-evaluation}
% ---------------------------------------------------------------------------

L'évaluation de la qualité du clustering nécessite de calculer la SSE sur les
données originales et non uniquement sur le coreset.

Cette étape est distribuée avec Spark afin que chaque partition calcule
localement sa contribution au coût global.

La méthode \texttt{CostEvaluator.cost} suit trois étapes :

\begin{enumerate}
    \item diffusion des centres à l'aide d'une variable broadcast ;
    \item calcul du coût local sur chaque partition ;
    \item agrégation des coûts partiels.
\end{enumerate}

L'implémentation est la suivante :

\begin{verbatim}
def cost(
  points: RDD[Point],
  centers: Array[Array[Double]],
  depth: Int = 2
): Double = {

  val bcCenters =
    points.sparkContext.broadcast(
      centers
    )

  points
    .mapPartitions { it =>
      Iterator.single(
        KMeans.cost(
          it.toArray,
          bcCenters.value
        )
      )
    }
    .treeReduce(
      _ + _,
      depth
    )
}
\end{verbatim}

Les centres sont suffisamment petits pour être diffusés à l'ensemble des
exécuteurs. Chaque partition calcule ensuite la SSE de ses propres points,
puis les contributions sont additionnées.

Contrairement à la fusion des coresets, cette réduction ne modifie pas la
structure du clustering : elle correspond uniquement à une somme de coûts
locaux.

Cette méthode est utilisée dans le protocole expérimental du
chapitre~\ref{ch:evaluation}. Le coût reporté dans les expériences est ainsi
toujours évalué sur les observations originales, même lorsque les centres ont
été calculés à partir d'un coreset.

\section{Lecture distribuée de Covertype pour les expériences}
% ---------------------------------------------------------------------------

Les premières versions du protocole expérimental chargeaient le jeu de données
Covertype dans un tableau local avant de le convertir en RDD avec
\texttt{parallelize}. Cette approche était suffisante pour les petits tests,
mais elle faisait transiter l'ensemble des observations par le driver avant
leur distribution.

Pour les expériences finales, le fichier est lu directement par Spark :

\begin{verbatim}
spark.sparkContext
  .textFile(path, numPartitions)
  .flatMap { line =>
    parseCovertypeLine(line, dim)
  }
\end{verbatim}

Le pipeline devient ainsi :

\[
\text{fichier}
\rightarrow
RDD[String]
\rightarrow
RDD[Point].
\]

Cette modification évite la construction préalable d'un grand
\texttt{Array[Point]} sur le driver et correspond mieux au modèle distribué
étudié dans ce projet.

Pour la référence séquentielle, le fichier est au contraire parcouru à l'aide
d'un itérateur. Les points sont transmis progressivement au
\texttt{BucketManager} sans charger l'ensemble du jeu de données en mémoire.

Une seconde lecture du fichier peut être effectuée après le calcul des centres
afin d'évaluer la SSE sur toutes les observations. Cette seconde passe
appartient au protocole de mesure et non à la construction du coreset
elle-même.

\section{Adaptation à Structured Streaming}
\label{sec:impl-streaming}
% ---------------------------------------------------------------------------

La version distribuée précédente traite un ensemble borné de données.
\texttt{StreamKMPlusPlus.run} étend cette logique à Structured Streaming en
utilisant \texttt{foreachBatch}.

Une version simplifiée du traitement est la suivante :

\begin{verbatim}
def run(
  source: DataFrame,
  p: StreamKMParams,
  onModel: KMeansModel => Unit,
  featuresCol: String = "features"
): StreamingQuery = {

  val global =
    new BucketManager(
      p.m,
      p.seed
    )

  source.writeStream
    .foreachBatch { (batch, batchId) =>

      val points =
        batch.rdd.map { row =>
          Point(
            row
              .getAs[Seq[Double]](
                featuresCol
              )
              .toArray
          )
        }

      val partial =
        mergeCoresets(
          points,
          p.copy(
            seed =
              p.seed + batchId
          )
        )

      partial.foreach(
        global.insert
      )

      val model =
        KMeans.fit(
          global.extractCoreset(),
          p.k,
          p.nRestarts,
          seed = p.seed
        )

      onModel(model)
    }
    .start()
}
\end{verbatim}

Chaque micro-batch suit donc deux niveaux de traitement.

D'abord, les observations du lot sont distribuées entre les partitions et un
coreset du micro-batch est calculé à l'aide de \texttt{mergeCoresets}.

Ensuite, le résumé obtenu est intégré à un état global conservé sur le driver.
Un nouveau clustering peut alors être calculé à partir du résumé courant.

Cette approche permet de maintenir un état de taille limitée entre les
micro-batches. Elle ne doit cependant pas être présentée comme strictement
équivalente à l'insertion directe de tous les points bruts dans un unique
\texttt{BucketManager}. Le résumé d'un micro-batch contient déjà des points
pondérés issus d'une réduction précédente. Cette différence constitue une
limite de l'adaptation actuelle et doit être prise en compte dans
l'interprétation de la version streaming.

\section{Réévaluation périodique et limites de l'état Spark}
\label{sec:impl-requetes}
% ---------------------------------------------------------------------------

L'implémentation actuelle recalcule un modèle à la fin de chaque micro-batch
grâce à \texttt{foreachBatch}. Elle fournit donc déjà une forme de
réévaluation périodique du clustering.

Elle ne reproduit toutefois pas l'ensemble de la variante à requêtes décrite
dans la thèse de référence. Celle-ci prévoit notamment le calcul simultané de
plusieurs valeurs de $k$, la conservation d'un état distinct pour chaque
configuration et la possibilité d'interroger cet état depuis l'extérieur du
job.

Ces fonctionnalités ne sont pas implémentées dans notre version.

Le calcul simultané de plusieurs valeurs de $k$ pourrait être ajouté en
réutilisant le même coreset courant :

\begin{verbatim}
Seq(25, 50, 75)
  .map { k =>
    KMeans.fit(
      coreset,
      k
    )
  }
\end{verbatim}

En revanche, la fonctionnalité de \textit{Queryable State} utilisée par Flink
n'a pas d'équivalent direct dans l'architecture retenue avec Spark Structured
Streaming.

Les résultats peuvent être transmis vers un système externe, un sink ou une
fonction de callback, mais l'état interne du traitement n'est pas exposé de la
même manière que dans Flink.

\section{Synthèse du portage Flink vers Spark}
\label{sec:portage-flink-spark}
% ---------------------------------------------------------------------------

Le portage de StreamKM++ ne correspond pas à une traduction directe de chaque
opérateur Flink. Certains mécanismes possèdent un équivalent proche dans
Spark, tandis que d'autres doivent être réorganisés en fonction du modèle
d'exécution du framework.

Les principales différences observées sont les suivantes :

\begin{itemize}

    \item La construction des coresets locaux se transpose naturellement :
    une partition Spark joue un rôle similaire à un subtask chargé de
    consommer un sous-ensemble du flux.

    \item La fusion des résumés est exprimée avec \texttt{treeReduce}, ce qui
    permet d'organiser les opérations de combinaison sur plusieurs niveaux
    plutôt que de centraliser immédiatement tous les résultats sur le driver.

    \item La diffusion des centres utilisée pour calculer le coût est
    directement prise en charge par les variables \texttt{broadcast} de
    Spark.

    \item Structured Streaming fournit explicitement les frontières des
    micro-batches avec \texttt{foreachBatch}, ce qui modifie la manière de
    représenter certaines étapes de contrôle du flux présentes dans
    l'implémentation Flink.

    \item Le partitionnement des données et les ressources de calcul peuvent
    être étudiés séparément dans Spark. Le nombre de partitions détermine la
    décomposition du traitement, tandis que le nombre de c\oe{}urs disponibles
    détermine le parallélisme réellement exploitable.

    \item Certaines fonctionnalités propres à Flink, notamment
    \textit{Queryable State}, ne disposent pas d'un équivalent direct dans
    l'architecture Spark retenue.

\end{itemize}

Ces différences montrent que le portage ne consiste pas seulement à remplacer
les API Flink par leurs équivalents Spark. Il nécessite également d'adapter le
dataflow et la gestion de l'état au modèle d'exécution du framework cible.
Les conséquences de ces choix sont étudiées expérimentalement au
chapitre~\ref{ch:evaluation}.
